# autodoc

CLI tool for helping AI coding agents find, navigate and use documentation inside a repository. Built in Go (latest stable), compiled to a single binary.

Doc files are markdown with YAML frontmatter containing `title`, `summary`, and `hash` keys.
By default, autodoc discovers docs recursively across the repo:
- find directories named `docs`
- include `.md` files recursively under each

`docsDir` is still honored as a compatibility inclusion root, even when not named `docs`.

---

## Configuration

`.autodoc/docs.json` in the repo root. If absent, all values use defaults. The `init` command creates the `.autodoc/` directory with a `.gitignore` that tracks only `docs.json`.

```json
{
  "docsDir": "./docs",
  "agentFiles": ["AGENTS.md", "CLAUDE.md"],
  "parallelism": 4,
  "ignores": []
}
```

| Key           | Default                        | Description                          |
|---------------|--------------------------------|--------------------------------------|
| `docsDir`     | `"./docs"`                     | Compatibility docs root to always include |
| `agentFiles`  | `["AGENTS.md", "CLAUDE.md"]`   | Agent memory files to update         |
| `parallelism` | `4`                            | Number of parallel groups for `fix`  |
| `ignores`     | `[]`                           | Glob patterns matched against repo-relative doc paths and filenames |

---

## Frontmatter Format

```yaml
---
title: "Getting Started"
summary: "Setup instructions for new users"
hash: "a1b2c3d4"
---
```

- **`title`** — Human-readable document title
- **`summary`** — One-line summary of the document's content
- **`hash`** — First 8 chars of MD5 hex digest, computed from all other frontmatter keys sorted alphabetically and concatenated, plus the document body content appended at the end

## CLI Commands

### `autodoc init`

Initializes a project for autodoc:

1. Create `docs.json` with defaults (if it doesn't exist)
2. Create `./docs` directory (if it doesn't exist)
3. Run `autodoc tree` to show current state
4. If files are missing correct frontmatter, advise the user to run `autodoc fix`

### `autodoc tree`

Pretty-prints all doc files with title and summary in tree format.

```
./
├── docs/
│   ├── getting-started.md — "Getting Started" — Setup instructions for new users
│   └── architecture.md — "Architecture" — Overview of system design and components
└── services/
    └── payments/
        └── docs/
            └── endpoints.md — "API Endpoints" — List of available endpoints
```

`autodoc tree` always shows a single unified repo-root view.
Git submodule docs are excluded by default.

### `autodoc stale`

Lists files where `hash` doesn't match the computed hash, or files missing frontmatter / required keys.

Same tree format as `autodoc tree`, but displays **Stale** in red instead of the summary.
Paths are repo-relative in the unified repo-root tree.

| Exit Code | Meaning             |
|-----------|---------------------|
| `0`       | No stale files      |
| `1`       | Stale files found   |

### `autodoc agents`

Inserts documentation indexes into agent memory files.

**Behavior:**

1. Discover all docs recursively using the same set as `tree`/`stale`/`fix`/`search reindex`.
2. For each doc, find the nearest ancestor directory that contains one or more configured agent files.
3. If multiple configured agent files exist at that nearest level (for example both `AGENTS.md` and `CLAUDE.md`, or one symlinked to the other), update all of them with the same generated index block.
4. If no ancestor owner exists, use existing root-level configured files; if none exist, create root fallback owner (`agentFiles[0]`).

*Auto-generated by `autodoc`. Do not edit manually.*

Use `autodoc` to search and maintain docs.

### Search

Use `autodoc search keyword <query>` to find relevant docs by keyword (BM25 full-text search).

```
autodoc search keyword "auth middleware protection"
```

Run `autodoc search reindex` to rebuild the search index after adding or changing docs.

### Linking Code to Docs

Add an `[autodoc()]` comment above any code block that implements or depends on a doc.
This creates a two-way freshness link — `autodoc fix` will warn when either the doc or the code drifts.

```
// [autodoc(<docId>@<docHash>, <scopeHash>)]
```

- `docId` and `docHash` come from the doc's frontmatter (`id` and `hash` fields).
- `scopeHash` is computed automatically by `autodoc fixed` from the code below the tag.
- Place the comment on the line directly above the relevant function, struct, or block.
- Run `autodoc fix` to validate all links and get instructions for updating stale hashes.

**When to add one:** whenever code implements behavior described in a doc, so that future changes to either side surface as staleness.

The index follows llms.txt conventions: each entry is a markdown link with the summary as description. Files are grouped under **bold** parent directory headers and sorted by filename within each group. Paths are repo-relative and collision-free across multiple docs roots.

### `autodoc fix`

Outputs text instructions for an AI agent to follow. Provides full context on what is broken and exact steps to fix each issue:

1. Add frontmatter to any doc files missing it (`title` set to filename without extension).
2. Run `autodoc stale` to identify all stale docs.
3. Group docs into sets (based on `parallelism` config).
4. For each file:
   - Update the summary to accurately reflect the content.
   - Rewrite default/missing titles to a pretty-print version of the filename or main H1.
   - Run `autodoc fixed <repo-relative-doc-path>` to recalculate the hash.
5. Run `autodoc agents` to update agent memory files.

### `autodoc fixed <filepath>`

Recalculates and writes the `hash` for a single doc file. Sorts all frontmatter keys alphabetically (excluding `hash`), concatenates values, appends the document body content, takes first 8 chars of the MD5 hex digest, and updates the file in place.

## Build

After any code change, run all tests then run `./install_locally.sh` to rebuild and install the binary to `~/.local/bin/autodoc`.

## Testing

Comprehensive unit tests. Each test fixture creates its own temporary workspace with doc files, runs commands, asserts output, and tears down on completion.
